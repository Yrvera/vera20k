# GSI-09.04 — Resource growth and spread scheduling: disparity scan

Date: 2026-09-05. Read-only. Binary: gamemd.exe (image base 0x400000) via Ghidra MCP; retail data `ini/rulesmd.ini`, `ini/artmd.ini`. Rust: worktree `clean-slate-system-impl-891469` @ `4b89ef52`.

Headline: the native per-type queue machinery (rebuild, AddTo*Queue, both processors, Place/Reduce feeds, timers, save/load restart, OreTwinkle pass) is implemented and **is the production path**. The 2026-07-30 gap-scan residuals are gone: the spread feed executes (`place_tiberium` existing-cell branch + the processor's explicit `AddToSpreadQueue`), no `#[ignore]` remains in `ore_growth.rs`, and the legacy scan/reservoir processor is an unreachable fallback. One stock-visible DRIFT remains: **the growth driver's reload interval**. gamemd reloads `ftol(Growth × 0.3)` whenever `ScenarioClass` SpecialFlags bit `0x40` is set — and every skirmish/multiplayer session start forces that bit on — so stock Riparius growth fires every ~660 frames; Rust reloads the raw `Growth=2200`. Everything else in the lane is MATCH (bounded), mod/map-only DRIFT, rare DRIFT, or EXCLUDED.

## 2. Rust production path (what `advance_tick` actually executes)

`Simulation::advance_tick` (`src/sim/world/mod.rs:6748`) → after trigger polling and `tick_scenario_lighting_transition`, **before** superweapon effects, radiation, the Team pass and the per-object AI/Phase-1 movement, it calls `tick_ore_growth_rungs` (`mod.rs:6897` → `mod.rs:3914`). That function:

- computes `native_growth_ready = !tiberium_types.is_empty() && classes.len() == tiberium_types.len() && overlay_grid.is_some() && overlay_registry.is_some()` (`mod.rs:3920-3930`);
- if ready: `OreGrowthState::tick_native_growth_driver` (`mod.rs:3941`, body `ore_growth.rs:734`) then `tick_native_spread_driver` (`mod.rs:3957`, body `ore_growth.rs:1017`), both on `self.scenario_rng` with `self.session.binary_frame`;
- else: legacy `ore_growth::tick_ore_growth` (`mod.rs:3976`, body `ore_growth.rs:1914`, RA1 scan/reservoir).

`classes.len() == tiberium_types.len()` is established by `rebuild_native_tiberium_queues_from_overlays` at every load seam: fresh authored/generated load (`scenario_post_map.rs:98`, `runtime.rs:889`) and snapshot restore (`snapshot.rs:1894`). The only production branch that leaves it at 0 is the no-`overlay_grid` branch (`scenario_post_map.rs:110-121`), i.e. no real map. **Legacy `tick_ore_growth` is therefore unreachable on a loaded map** (fixture/headless only). The per-tick order is: native growth for all due types → native spread for all due types → later Phase 7 `tick_terrain_spawners` (TIBTRE `PlaceTiberium` through the same `place_tiberium`/`add_native_growth_queue_cell`, `terrain_spawn.rs:722`).

Cell-mutation seams feeding the queues: `sim::tiberium::place_tiberium` (`tiberium/mod.rs:314`) and `reduce_tiberium` (`tiberium/mod.rs:441`); harvest goes through `reduce_tiberium_at_with_native_context` (`miner_system.rs:1065/1408` → `world/mod.rs:3600`), combat/smudge through `dispatch_tiberium_reduction_inline` (`world/mod.rs:1001`). Hash: `world_hash.rs:1009` → `OreGrowthState::hash_state` (timers, entry arrays, heaps, bitmaps).

## 3. Per-mechanism findings

Frequency scale for an ordinary stock skirmish: growth processor fires per type every reload interval (see M2); spread every 2200 frames; each fire touches 5..50 / 5..25 popped entries.

### M1 — Tick integration and driver order — MATCH (bounded)
Native `0x0055B4D7/0x0055B4DC`: all-type growth driver, then all-type spread driver, before Bomb/Team/logic-vector updates. Rust `tick_ore_growth_rungs` runs growth then spread before `run_team_script_pass` and object AI (`mod.rs:6897-6912`). Scenario-RNG stream identity: all native draws use `Scen+0x218` (`ORE_GROWTH_RNG_STREAM_ROUTING` report, spot-checked at `0x007224AE`/`0x0072303F`); Rust uses `scenario_rng` throughout. MATCH.

### M2 — Growth driver timer reload — **DRIFT (stock-visible, continuous)**
Native `0x00722C9E..0x00722CE3` (disassembled this session): after `GrowthProcessor` returns, `TEST byte [ScenarioClass],0x40`; set → `FLD [0x007E5138]` (0.3), clear → `FLD [0x007E1718]` (1.0); `FILD [this+0xA8]` (`Growth`); `FMUL`; `CALL Math__ftol`; write `+0x11C = frame`, `+0x124 = result`.
Bit `0x40` state in a stock skirmish: the session start paths OR `0xC0` into `DAT_00A8E960` (`0x005B6ACF`, `0x005B7326`, `0x005BB209`, `0x005E74CD`, all read this session), and `ScenarioClass::Full_Init` copies `DAT_00A8E960` into `ScenarioClass` dword 0 when `DAT_00A8B238 != 0` (`0x00687C1E..0x00687C29`). Map `[SpecialFlags] TiberiumGrows/TiberiumSpreads` are not applied in that session type (`SPECIAL_FLAGS_SYSTEM.md`, campaign-only list). So in skirmish the multiplier branch is always 0.3.
Rust `tick_native_growth_driver` (`ore_growth.rs:783-790`): `interval: scaled_timer_interval(ty.growth, TIMER_MULTIPLIER_PPM)` = `Growth` unscaled (`ore_growth.rs:1718`, `TIMER_MULTIPLIER_PPM = 1_000_000` both operand and divisor) → **2200**. No `0.3` anywhere in `ore_growth.rs`.
Concrete: native Riparius growth cadence ≈ 660 frames (fires at frames 0, ~660, ~1320, …); Rust 2200 (0, 2200, 4400, …). Over a 30-minute skirmish at 60 fps (108 000 frames) native runs ≈164 growth processor calls per type, Rust 49. Each call grows up to 50 cells one density step and feeds `AddToSpreadQueue`, so both densification and the spread queue's runtime feed are ~3.3× slower in Rust. Player-visible: harvested fields recover density much more slowly; long-game income diverges. Frequency: every match, all game long.
Exact value caveat: the driver report's "660" is a hand calculation. The process runs 53-bit **chop** rounding (`util/native_x87.rs:3`); `2200 × 0x3FD3333333333333` is `659.99999999999997558…`, which chops to `659.99999999999988631` and `Math__ftol` truncates to **659**. The builder must evaluate through `X87Chop53::mul` + `ftol_i64` (as `native_processor_batch` already does) rather than hardcode either number; confirm with a native emulation of `0x00722CA9..0x00722CD3` or a retail capture before pinning a golden.
Spread reload (`0x0072221C`: raw `+0x9C`) — Rust `scaled_timer_interval(ty.spread, PPM)` = 2200. MATCH.

### M3 — Driver gates and the flag composition — DRIFT (mod/map-only, dormant on stock data)
Native: both drivers and `CanGrowTiberium`/`GrowTiberium`/`PlaceTiberium`(existing) gate only on `ScenarioClass+0x34A6` (`[Basic] TiberiumGrowthEnabled`, default 1 from `Set_Defaults @0x00683610`, read at `0x0068A589`); `CanSpreadTiberium`/`SpreadTiberium` gate on SpecialFlags bit `0x80`; `[General] TiberiumGrows/TiberiumSpreads` and map `[SpecialFlags]` do not gate anything in a skirmish (bits 6/7 are forced on).

The rebuild seams pass `basic.tiberium_growth_enabled.unwrap_or(true)` for growth and `General.TiberiumSpreads && SpecialFlags.TiberiumSpreads` for spread (`scenario_post_map.rs:104-106`, `runtime.rs:893-894`).

### M8 — `AddToGrowthQueue` / `AddToSpreadQueue` — MATCH except the array-counter rebuild trigger — DRIFT (rare)
Native growth: `OverlayData < 0x0B` (no dedupe), **`entry_counter (+0x10C) > capacity − 10` → `RebuildGrowthQueue`**, append, one `Next`, priority `abs(Next) % 50 + frame` (float), heap insert only if `heap_count + 1 < capacity`, flag set. Spread: `CanSpreadTiberium && flag == 0`, **`entry_counter (+0xF0) >= capacity − 0x14` → `RebuildSpreadQueue`**, same insert shape. Rust `add_native_growth_queue_cell` / `add_native_spread_queue_cell_for_type` (`ore_growth.rs:619-732`) match the admission, RNG draw, priority (`growth_queue_priority`, signed-abs then `% 50`), heap/array behaviour (`NativeTiberiumQueue::push`, `ore_growth.rs:284`), and flag set; the counter-triggered rebuild is intentionally not modelled (comment cites OQ-38). The counter only resets on a rebuild and grows by every processor reinsert plus every admitted add. With capacity `(H+4)·W·2` (e.g. 150×150 → 46 200; 60×60 → 7 680) and ≤50 growth reinserts per ~660-frame fire, a small map in a multi-hour game can cross `capacity − 10`, after which gamemd rebuilds (priorities reset to 0, duplicates/stale entries dropped) and pop order changes. Frequency: rare (small maps, very long games); effect: growth/spread order divergence, not correctness.
