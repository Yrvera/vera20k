## Look up dependency chains

Each row is `source -> dependency; dependency`. Paths omit the `vera20k::`
prefix; `vera20k` itself is the crate root. `-` means no cross-module dependency
was emitted for that module in this snapshot. All rows are sorted and include
private modules. Each row describes that module, not its entire descendant tree.

From the repository root:

```powershell
# What does this exact module depend on?
rg -n '^sim::movement -> ' docs/module-map.md

# Which modules depend on this exact module? Match a complete destination.
rg -n -- ' -> (.*; )?sim::movement(;|$)' docs/module-map.md

# Inspect the movement module and its children together.
rg -n '^sim::movement(::[^ ]+)? -> ' docs/module-map.md
```

To follow `A -> B -> C`, read A's row, select B, then read B's row. For reverse
chains, look up incoming rows at each step. Keep a visited set: cycles and
re-exports are expected; they do not by themselves establish an architectural
bug. If a row is absent, check its parent, the structure tree and the current
source/build configuration instead of guessing a dependency.

For example, this snapshot contains the module dependency chain
`sim::movement -> sim::pathfinding::core -> map::resolved_terrain`.
Read each hop's source before treating it as relevant to a gameplay mechanism.

### What these edges mean

- Only cargo-modules **`uses`** edges become dependencies. Structural **`owns`**
  edges are excluded; they describe containment, not gameplay state ownership.
- Item endpoints are grouped under their nearest module in the tool's qualified
  symbol paths; repeated edges and edges within the same module are removed.
  An impl method can be attached to its type's module even when its source lives
  in another file. Consult source for the physical implementation location.
- cargo-modules 0.26.0 gathers module-scope imports/re-exports and type relations
  such as parameter, return and field types. Its function analysis does **not**
  walk function bodies to construct a call graph. See the pinned
  [graph builder](https://github.com/regexident/cargo-modules/blob/v0.26.0/src/graph/builder.rs).
- A chain establishes static module relationships, not execution order, an
  end-to-end production path, exhaustive change impact, or `gamemd` parity.
  Missing edges are not evidence that no runtime dependency exists. Follow
  actual callers, implementations and tests for those conclusions.

## Refresh the generated views

Use the checkout being analyzed. Follow [ENGINE.md](../ENGINE.md) before Cargo:
wait for other owners' Cargo/rustc work and preserve their files and processes.
The formatter requires cargo-modules 0.26.0 and committed source/build inputs;
initial analysis can compile build scripts and procedural macros.

```powershell
python tools/module_map.py
# Regenerate and compare the tree/dependencies without rewriting this file:
python tools/module_map.py --check
```

The formatter runs these existing tool commands and updates only the marked
sections below. It preserves this navigation guide. A documentation-only commit
does not require a new snapshot solely to change its recorded source revision.
Refresh after changing source dependencies, module layout, visibility, features
or target; the saved views describe only the recorded build scope.

```powershell
$env:NO_COLOR = "1"
cargo modules structure --lib -p vera20k --target x86_64-pc-windows-msvc --no-fns --no-traits --no-types
cargo modules dependencies --lib -p vera20k --target x86_64-pc-windows-msvc --no-externs --no-sysroot
```

Keep function/type nodes in the raw dependency graph: their `uses` edges are
included when the formatter groups endpoints into modules. To inspect the
underlying item relationships, capture that raw DOT output locally and search
for the full `vera20k::...` symbol paths. Formatting needs no graph database,
Graphviz installation or additional Python packages.
