Date: 2026-05-27

**Slot:** /re-swarm soviet-sidebar-final-pixel-blockers slot 3  
**Target:** `MINIMAP_GENERATED_PIXEL_COLOR_PIPELINE`  
**Address(es):** `RadarClass__Draw @ 0x00653100`, `RadarClass__GenerateTerrainSurface @ 0x006547C0`, `RadarClass__FillTerrainColors @ 0x00654EA0`, `RadarClass__RenderCellPixel @ 0x00655C50`, `RadarClass__Update @ 0x00656EC0`, `CellClass__GetRadarColor @ 0x0047C060`, `OverlayClass__GetRadarColor @ 0x005FED00`  
**Investigation Mode:** coverage-map with a verified pipeline contract.  
**Confidence:** High for ordinary in-game pipeline ordering, shroud/fog/object branch behavior, generated-surface blit, and dirtying; Medium for exhaustive per-theater tile color constants because this pass did not decode every TMP/tile image source.  
**Active in YR:** Yes for ordinary sidebar radar when radar mode/state are active. Fog dimming is conditional; standard YR `FogOfWar=no` means unexplored shroud is the normal black-hidden state, while explored cells normally remain visible unless fog is explicitly enabled or a scenario/mod sets fog counters.

## Summary

The ordinary in-game minimap content is a generated DirectDraw-style surface pipeline, not a paletted sidebar SHP. `RadarClass` builds raw RGB terrain samples, packs them into a 16-bit secondary terrain surface, then updates a 16-bit primary display surface with object dots, shroud/fog, radar events, spy-satellite overlays, and viewport primitives. `RadarClass::Update` blits the changed primary-surface rect into `g_SidebarSurface` inside the already verified Soviet aperture, normally `(16,49)` with max `140x108`.

Terrain color starts in `CellClass__GetRadarColor`, object dots are packed from house/color-scheme data, unexplored shroud writes literal pixel `0`, fog dims terrain by channel `>> 1`, and visible terrain copies the prebuilt secondary-surface pixel. Dirtying is pixel/terrain-list driven, not a full minimap upload every frame.

## Verified Binary Findings

### 1. Pipeline has three content buffers/surfaces

Active in YR: Yes.

`RadarClass__GenerateTerrainSurface @ 0x006547C0` allocates and uses:

| Offset | Role | Evidence |
|---|---|---|
| `this+0x123C` | raw RGB terrain buffer, 3 bytes per radar-space pixel | `0x006547C0` allocates `param_3[2] * param_3[3] * 3`; `0x00654EA0` writes triples |
| `this+0x1220` | secondary/generated terrain BSurface, 16-bit packed pixels | `0x006547C0` constructs `BSurface` and packs raw RGB through DD loss/shift globals |
| `this+0x121C` | primary/live display DSurface, 16-bit packed pixels | `0x00654650` constructs clone-sized DSurface; `0x00655C50` writes final pixels |

The raw RGB buffer is zero-initialized on allocation before terrain fill. The secondary surface is generated by sampling the raw RGB buffer through the radar zoom/aspect-fit step and packing channels as:

```text
packed =
  ((R >> g_DD_RLoss) << g_DD_RShift) |
  ((G >> g_DD_GLoss) << g_DD_GShift) |
  ((B >> g_DD_BLoss) << g_DD_BShift)
```

Each channel is clamped to `0xFF` before packing. Evidence: `RadarClass__GenerateTerrainSurface @ 0x006547C0`, channel clamp/pack in the decompile and assembly context around `0x00655E8A` for the matching unpack/repack pattern.

### 2. Terrain raw RGB comes from `CellClass__GetRadarColor`

Active in YR: Yes.

`RadarClass__FillTerrainColors @ 0x00654EA0` iterates map cells, projects each cell to radar-space, clips a one- or two-pixel footprint, calls `CellClass__GetRadarColor`, and writes one or two RGB triples into `this+0x123C`.

Load-bearing details:

- Cell projection uses `(cell_x - cell_y)` / `(cell_x + cell_y)` style radar coordinates with map offsets already stored in `RadarClass`.
- Most cells write two adjacent raw RGB pixels; left/right edge cases write one pixel.
- The two output colors from `CellClass__GetRadarColor` are stored separately, so the two-pixel footprint can differ.
- `RadarClass__ClearBackground @ 0x00655250` reuses the same cell-color path for terrain dirty cells, then regenerates only the affected generated-surface rect.

Evidence: `0x00654EA0`, `0x00655250`, `0x0047C060`.

### 3. Base terrain color path applies theater brightness then halves channels

Active in YR: Yes.

When no radar-visible overlay path takes over, `CellClass__GetRadarColor @ 0x0047C060` resolves the cell's isometric tile type and tile subcell, loads the tile image/color entry, applies theater brightness with `ApplyTheaterBrightness`, then writes half-bright RGB to both output colors:

```text
out.R = brightened.R >> 1
out.G = brightened.G >> 1
out.B = brightened.B >> 1
```

If the resolved tile-color entry is missing, the fallback color is `(60,60,60)`.

Evidence:

- `0x0047C060` tile path: `FUN_00544E00`, optional `FUN_00544C80`, image entry read at `+0x2B/+0x2C/+0x2D`.
- `ApplyTheaterBrightness` call uses scenario theater table `&DAT_007E1BD0 + ScenarioClass+0x1258 * 0x70`.
- Channel halving occurs immediately after brightness before writing `param_2` and `param_3`.
- Fallback writes `0x3C,0x3C,0x3C`.

### 4. Overlay/tiberium terrain colors override tile colors

Active in YR: Yes, conditional on cell overlay data.

`CellClass__GetRadarColor @ 0x0047C060` checks cell overlay fields before normal terrain. Important cases:

- If a specific occupier RTTI `0x24` is found, both output colors become `(200,200,160)`.
- If cell flags include `0x100`, `OverlayClass__GetRadarColor` supplies the color.
- Several overlay IDs are explicitly excluded from one overlay branch: `-1`, `100`, `0x65`, `0xE7`, `0xE8`, and `0xEF`.
- Overlay IDs in ranges `0x4A..0x63` and `0xCD..0xE6` force the secondary parameter passed to `OverlayClass__GetRadarColor` to `1`; otherwise the cell byte at `+0x11E` is passed.
- Some overlay types with a non-null image/type pointer use `GetTiberiumRadarColor`; if `CellClass__OverlayToTiberiumIndex` returns non-`-1`, the fallback color is `(170,170,130)`.

`OverlayClass__GetRadarColor @ 0x005FED00` returns black `(0,0,0)` if the overlay has no usable image and no alternate object image. Otherwise it samples `GetTiberiumRadarColor`. For overlay indices `0x7F..0x8A` and `0x93..0x9E`, it byte-swaps the sampled RGB order before returning.

Evidence: `0x0047C060`, `0x005FED00`, `GetTiberiumRadarColor`.

### 5. `GetTiberiumRadarColor` samples SHP frame metadata, not `SIDEBAR.PAL`

Active in YR: Yes for overlay/tiberium radar color paths.

`GetTiberiumRadarColor` resolves an SHP, checks `frame_index < frame_count`, then reads three bytes from the frame header area at `frame + 0x0C..0x0E`. If no SHP/frame is available, it returns `(0,0,0)`.

This is independent of ordinary sidebar chrome palettes. It is a generated terrain/overlay color input, not a `CC_Draw_Shape` conversion through `SIDEBAR.PAL`.

Evidence: `GetTiberiumRadarColor` decompile.

### 6. `RenderCellPixel` applies object, fog, shroud, or terrain in that order

Active in YR: Yes.

`RadarClass__RenderCellPixel @ 0x00655C50` is the final per-pixel writer for the primary minimap surface. Its order is:

1. Early-out if no `g_PlayerPtr`.
2. Early-out if the requested radar pixel is outside primary surface rect.
3. Convert radar pixel back to map cell lepton center using the radar zoom/offset inverse transform.
4. Query shroud and fog only when `g_hWnd != 0`.
5. Scan the object tracker bucket for objects exactly at that radar pixel.
6. If an eligible object is found, write object color or flashing inverted object color.
7. Else if fogged, read secondary terrain pixel, unpack channels, halve, repack, and write.
8. Else if shrouded, write literal `0`.
9. Else copy the secondary terrain pixel directly to primary.
10. Expand `this+0x120C..0x1218` dirty rect to include the changed sidebar-local pixel.

Evidence: `0x00655C50`; assembly contexts `0x00655D3C..0x00655D87`, `0x00655E8A`, `0x00656058`, `0x00656081`, `0x0065608B`.

### 7. Unexplored shroud is black; fog is half-bright terrain

Active in YR: Shroud yes in standard YR; fog branch conditional.

`IsShrouded @ 0x00586360` returns true when the cell explored bit at cell `+0x12C` bit `0x08` is clear. `RenderCellPixel` writes literal pixel value `0` for shrouded cells when no eligible object overrides it.

`IsFogged @ 0x005864A0` returns true when cell `+0x13C >= 1`. If fogged, `RenderCellPixel` reads the secondary terrain pixel and halves each unpacked channel by unsigned `>> 1`, then repacks through the DirectDraw loss/shift globals. This is not a palette lookup and not an alpha blend.

Standard YR INI has `FogOfWar=no` in `rules.ini`; no `rulesmd.ini` override was found in this scan. Therefore the fog branch exists and is binary-live, but ordinary standard YR minimap parity should expect black unexplored cells and visible explored terrain unless a mode/scenario/mod activates fog counters.

Evidence: `0x00586360`, `0x005864A0`, `0x00655E8A..0x00656081`, `ini/rules.ini:172`, `ini/rules.ini:2520`.

### 8. Object dots are tracker-driven and use house/color-scheme color sources

Active in YR: Yes for radar-visible tracked objects.

`RadarClass__AddObjectToTracker @ 0x00655560` inserts objects into a 256-bucket tracker using:

```text
bucket = (pixel_x + pixel_y * -5) & 0xFF
```

Local-player objects are inserted at the front of the bucket; non-local objects append. `RenderCellPixel` scans the bucket forward and uses the first eligible object at the pixel. Removal compacts the 16-byte entries and marks the pixel dirty.

Object-color details:

- If the object has an owner/color source, `RenderCellPixel` packs bytes at owner/color object `+0x56F9`, `+0x56FA`, `+0x56FB` through DD loss/shift globals.
- If no owner/color source is available, it falls back to a prepacked value from `FUN_0068CA50()+0x330`.
- `RadarClass__RenderAllCells` has a no-window/full-refresh path that derives object color through `g_ColorSchemeArray`, color-scheme `+0x30C`, and index `+0x330`; this is a separate bulk path but lands in the same primary surface.
- A local-player object can flash/invert: if its timer fields allow `(remaining - 1) / RulesClass+0x88` to yield the tested odd phase, `RenderCellPixel` writes `~packed_color`.

Eligibility gates in `RenderCellPixel` include same-pixel match, shroud/human-player condition, `TechnoType` radar-invisibility/alliance condition at type `+0x22F`, and an additional type/attachment condition at `+0x232` / `+0xC9B`. The exact semantic names of the latter offsets were not relabeled in this read-only pass, but the branch order and fields are verified.

Evidence: `0x00655560`, `0x00655740`, `0x00655C50`, `0x00656150`.

### 9. Dirtying is incremental and feeds the sidebar-surface copy rect

Active in YR: Yes.

There are two major dirty sources:

- Terrain dirty cells: `RadarClass__MarkTerrainDirty @ 0x006551C0` deduplicates packed cell coordinates in the terrain dirty list at `+0x1228/+0x1234`, then sets `+0x14D9`.
- Pixel dirty cells: `RadarClass__MarkCellDirty @ 0x006562D0` bounds-checks the primary surface, sets a visited bit in `+0x1274`, appends the pixel to the dirty list at `+0x1260/+0x126C` if not already present, then sets `+0x14D9`.

`RadarClass__Update @ 0x00656EC0` responds to `+0x14D9`, viewport changes, object movement, terrain dirty counts, pixel dirty counts, and spy-satellite updates. It clears dirty terrain into the secondary surface, renders object/fog/shroud pixels into the primary surface, draws radar events and spy-satellite vision, then blits only the accumulated changed primary-surface rect into `g_SidebarSurface` when mode/state are active.

`RenderCellPixel` expands `this+0x120C..0x1218` by converting primary-surface pixel coordinates through `+0x149C/+0x14A0`; the rect expansion uses a `+2` width/height adjustment for one-pixel inclusivity in the non-empty case.

Evidence: `0x006551C0`, `0x006562D0`, `0x00655C50`, `0x00656EC0`.

### 10. Sidebar blit order is chrome frame, generated content, viewport primitives

Active in YR: Yes when active radar mode/state permit content display.

`RadarClass__Update @ 0x00656EC0` computes:

```text
active_content = (this+0x14B0 == 1 && this+0x14AC == 1)
```

When active and `force_redraw +0x14DA` is set, it draws `DAT_00B04A38` frame `0x20` to `g_SidebarSurface` at `(this+0x11E4, this+0x11EC)`, normally `(0,48)`, before content blit.

Then, if dirty rect width/height are positive, it calls `g_SidebarSurface` vtable `+0x08` to copy from primary surface `this+0x121C` into the sidebar dirty rect. The source rect is computed by subtracting the content destination origin `this+0x149C/0x14A0` from the sidebar-local dirty rect.

After the content blit, it draws viewport/selection primitives via `g_SidebarSurface` vtable `+0x58`, including an expanded border rect `(x-1, y-1, w+2, h+2)` around the content area.

Evidence: `0x00656EC0`, assembly context `0x006575E5..0x00657668`, and sibling report `SOVIET_RADAR_MINIMAP_CONTENT_INSET_GHIDRA_REPORT.md`.

### 11. Radar transition/movie can repaint chrome but does not make minimap content a SHP

Active in YR: Yes, conditional on radar mode/state.

`RadarClass__Draw @ 0x00653100` always calls `RadarClass__Update`, but mode `3` delegates to `RadarClass__PerFrameMovieUpdate @ 0x006579E0`. The movie/update path can draw `DAT_00B04A38` frame `0x20` and set the dirty rect to the full radar chrome area (`g_SIDEBAR_WIDTH_CONST x 0x6E`), but generated minimap content still comes from `this+0x121C` when the active mode/state path blits it.

Evidence: `0x00653100`, `0x006579E0`, `0x00656EC0`.

## Negative Facts / Do Not Do

- Do not derive ordinary minimap content colors from `SIDEBAR.PAL`, `CAMEO.PAL`, `OBSERVER.PAL`, or `RADAR.SHP` transparency. The content is a generated surface pipeline.
- Do not use `radar.shp` frame transparency to size or color the content. The settled aperture is a `RadarClass` field/BSurface blit path.
- Do not conflate tactical shroud rendering with minimap shroud; unexplored minimap pixels write literal packed `0`.
- Do not implement fog dimming as alpha blending. Native fog reads the packed terrain pixel, unpacks channels, does unsigned `>> 1`, and repacks.
- Do not redraw every minimap pixel every frame if the target is native flicker/dirty parity. Native tracks terrain and pixel dirty lists plus a visited bitfield.
- Do not sort or layer radar objects by a new Rust policy. Native object winner comes from the tracker bucket order and eligibility gates.
- Do not treat INI `RadarColor` as the only overlay/tiberium source. Some radar colors come from SHP frame metadata and special overlay branches.

## Remaining Uncertainty

- Exact semantic names for `TechnoType` fields `+0x22F`, `+0x232`, and `+0xC9B` in the object eligibility branch were not relabeled in this read-only pass. The offsets and branch behavior are verified.
- Full TMP/tile image color extraction helpers (`FUN_00544E00`, `FUN_00549E50`, `FUN_004814F0`) were touched through callers but not exhaustively drained. A follow-up can produce a complete per-theater tile color contract.
- Runtime DirectDraw descriptor values (`g_DD_RLoss/RShift/GLoss/GShift/BLoss/BShift`) were not sampled from a live process; formulas are verified, live standard 16-bit format values are deferred.
- Fog branch liveness under unmodified standard YR play was verified as conditional from INI defaults and binary gates, not by live runtime frame capture.
- `DrawSpySatelliteVision` and radar-event pixels were identified in the update order but not decoded for exact pixel shapes/colors in this report.
