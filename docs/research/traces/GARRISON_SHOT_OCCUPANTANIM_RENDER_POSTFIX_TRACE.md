# Garrison Shot OccupantAnim Render Postfix Trace

Date: 2026-05-27
Scope: one healthy occupied static civilian garrison fires one occupant shot. Concrete stock case: `CAGAS01` with one occupant using `UCPara`, so the shot visual is `OccupantAnim=UCFLASH`.

## Scenario Inputs

- `CAGAS01`: `TechLevel=-1`, `Strength=1000`, `CanBeOccupied=yes`, `MaxNumberOccupants=10`, `CanOccupyFire=yes` (`ini/rulesmd.ini:19302..19325`).
- `CAGAS01` art: no active `ActiveAnim` keys, commented `ActiveAnim`, and active `MuzzleFlash0..9` offsets (`ini/artmd.ini:8019..8041`).
- `UCPara`: `OccupantAnim=UCFLASH` (`ini/rulesmd.ini:22944..22953`).

Healthy body render -> optional active/idle building anim slot replacement -> occupied shot fire event -> `OccupantAnim` selection -> garrison fire-port origin -> app-layer `GarrisonMuzzleFlash` spawn -> frame cadence/deletion -> sprite instance depth/order.

## Adjacent Findings

- Healthy body frame equality here does not clear damaged occupied BState parity; Rust still uses health ratio as a proxy for native `Building+0x534`.
- `CAWASH19 ActiveAnimGarrisoned=CAWA19_AG` is not a standard active garrison in YR because the relevant `CanBeOccupied` flags are commented out; it is outside this concrete scenario.
- Non-garrison weapon `Anim=` muzzle flashes and the chrono sparkle branch are separate presentation paths and were not traced here.

## Top Player-Visible Findings

1. Stage: z-adjust depth behavior. Player-visible difference: the occupied shot flash can sort at the wrong depth relative to building parts, walls, or nearby sprites because Rust uses `-200` as a screen-row shift instead of a native Z-adjust/depth-bias input. Rust: `src/app_instances/overlays.rs:511..512`, `src/app_instances/helpers.rs:43..52`. gamemd evidence: `anim+0x100=-200` in occupied `Fire_At` and Z-adjust as depth bias (`docs/research/CONTINUOUS_GARRISON_MUZZLE_FLASH_CADENCE_GHIDRA_REPORT.md:108..116`; `docs/research/CELL_COMPUTE_ZADJUST_FORMULA_GHIDRA_REPORT.md:254..266`).
2. Stage: runtime frame cadence. Player-visible difference: flash frame changes can occur one app frame early/late versus native logic AI cadence because Rust advances by wall-clock `dt_ms`, not the generic `AnimClass::AI` tick countdown. Rust: `src/app_sim_tick.rs:181..195`, `src/app_building_anim.rs:746..763`. gamemd evidence: generic `AnimClass::AI @ 0x00423AC0` rate countdown (`docs/research/CONTINUOUS_GARRISON_MUZZLE_FLASH_CADENCE_GHIDRA_REPORT.md:126..131`).
3. Stage: generic AnimClass lifecycle fields. Player-visible difference: stock or modded `OccupantAnim` sections using `End`, `LoopStart`, `LoopEnd`, `LoopCount`, `Next`, `Shadow`, `PingPong`, or `RandomRate` will end, loop, chain, or shadow incorrectly because Rust deletes at raw SHP frame count. Rust: `src/sim/components.rs:529..536`, `src/app_building_anim.rs:746..755`. gamemd evidence: generic lifecycle in `AnimClass::AI` (`docs/research/CONTINUOUS_GARRISON_MUZZLE_FLASH_CADENCE_GHIDRA_REPORT.md:128..131`, `227`).
