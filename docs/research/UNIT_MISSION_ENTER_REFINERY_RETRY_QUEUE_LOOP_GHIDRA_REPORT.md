# Unit Mission Enter Refinery Retry Queue Loop - Ghidra Research Report

**Address(es):** `0x004D9290` primary (`FootClass__Mission_Enter`, mission-table slot `+0x240` for mission ID `7`); supporting `0x004D8FB0`, `0x004D94B0`, `0x0043C2D0`, `0x0065AD30`, `0x0040DD70`, `0x005B3060`, `0x005B3A00`.
**Investigation Mode:** exhaustive-slice
**Claimed Scope:** retry/queue behavior inside the `0x004D9290` mission handler after a harvester is in Mission Enter for a refinery: repeated `CAN_DOCK`, waiting state, accepted-cell movement handoff, abort/preserve behavior, and target preservation.
**Non-Scope:** full `BuildingClass::Receive_Radio` case `0x0E` internals, war factory exit, repair/hospital/armory/carrier enter behavior except where `0x004D9290` shares the same dispatcher, and runtime debugger frame counts for the mission timer table value.
**Confidence:** High for branch behavior and field effects verified from decompilation/assembly; Medium for exact frame cadence because the mission timer table value was not decoded from runtime-initialized data in this slot.
**Active in YR:** Yes. Mission ID `7` dispatches through vtable slot `+0x240` to `0x004D9290` in `MissionClass::Mission_Dispatch @ 0x005B3060`, and stock `[CMIN]/[HARV] Dock=NAREFN,GAREFN` plus `DockUnload=yes` refineries use this path.

## 1. Overview

`0x004D9290` is the compact FootClass Mission Enter handler used by UnitClass vehicles through the mission table. For refinery docking, it does not allocate or manage a queue itself. It selects the current radio contact or a filtered fallback target, transmits `CAN_DOCK(0x0E)` to that object, preserves Mission Enter when the request is accepted or the unit already has the dock-entered flag, and otherwise breaks contact and aborts movement.

The queue-cell move is not generated by this handler. It is produced by `BuildingClass::Receive_Radio @ 0x0043C2D0` case `0x0E`, and installed on the harvester by `FootClass::Receive_Radio @ 0x004D8FB0` case `0x12`.

## 3. Core Logic

1. Mission Enter first asks `RadioClass` contact slot `0` for a target (`0x0065AD30`, called with index `0`). If that returns null, it filters `this+0x218` through `0x0040DD70`, accepting only abstract types `1`, `2`, `6`, or `0xF`.
2. If no target survives, it checks the helper at `0x0070D8F0`. If that does not retarget the unit, and `+0x5A4` is null or not abstract type `1`/`2`, it calls vtable `+0x484` with `(0,1)` and then vtable `+0x1EC`.
3. If a target exists, it sends `Transmit_Radio(0x0E, target)` through vtable `+0x278`.
4. If the `0x0E` return is `1`, Mission Enter proceeds. If the return is not `1` but byte `+0x418` is nonzero, it also proceeds. If the return is not `1` and `+0x418` is zero, it sends `BREAK(0x03)` via vtable `+0x274`, calls vtable `+0x484(0,1)`, and exits to the standard timer epilogue.
5. After accepted/preserved `CAN_DOCK`, if `+0x5A4` is null and `+0x598 > 0`, it may query IPiggyback on `+0x674`, then consumes the first queued entry at `+0x58C`, calls vtable `+0x480(entry,0)`, decrements `+0x598`, and shifts the remaining entries down one slot.
6. If `+0x5A4` is nonzero, Mission Enter skips that queued-entry consumption. For Teleporter types (`Type+0xCD4 != 0`), it clears `+0x5A0/+0x5A4` and calls vtable `+0x480(old_navcom,1)`.
7. The epilogue returns the standard mission delay: `ftol(MissionTimerEntry(current_mission)[+0x10] * 900.0) + RandomRanged(0,2)`.

For a standard refinery, `BuildingClass::Receive_Radio` case `0x0E` sends `0x12` with the accepted cell. `FootClass::Receive_Radio` case `0x12` returns `0x14` if the unit is already on that cell; otherwise it calls `Set_Destination(*payload,1)`, writes `+0xC8 = current frame`, writes `+0xCC = payload Y local`, clears `+0xD0 = 0`, and returns `1`. This is the movement retry reset point.

## 5. Integration Points

`MissionClass::Mission_Dispatch @ 0x005B3060` calls mission ID `7` through vtable slot `+0x240`. The `0x004D9290` function has only vtable data xrefs, consistent with mission-table dispatch rather than ordinary direct calls.

`BuildingClass::Receive_Radio @ 0x0043C2D0` case `0x0E` owns the accept/reject details and the accepted-cell payload. This report relies on sibling reports for the settled `anchor+(3,1)` payload and non-use of `QueueingCell=`.

`FootClass::Receive_Radio @ 0x004D8FB0` case `0x13` returns `10` while a destination exists and locomotor reports active movement. In the building's `0x0E` path that becomes a silent preserve return, so a moving harvester is not re-commanded every frame. Case `0x12` performs the concrete SetDestination/reset when the building does decide to send a cell payload.

`FootClass::Set_Destination_Internal @ 0x004D94B0` writes `+0x5A4`, clears/restarts movement retry fields including `+0x6B7`, `+0x668/+0x66C/+0x670`, and walker retry fields `+0x640/+0x644/+0x648`.

## 6. Current Rust Implementation Status

Rust has a higher-level split that resembles the binary flow but is not timer-equivalent. `src/sim/miner/miner_dock.rs:42-78` implements HELLO/contact capacity and a Rust-side `waiting_retry_queue`. `src/sim/miner/miner_dock_sequence.rs:567-602` waits at `QueueingCell` until HELLO/contact admission succeeds, while gamemd standard `HELLO(2)` itself rejects a second miner when `NumberOfDocks=1`; this report did not prove a binary FIFO outside contacts.

`src/sim/miner/miner_dock_sequence.rs:604-630` models Mission Enter as an immediate accepted-cell issue/recheck phase. The binary instead re-enters `0x004D9290` on mission dispatch, sends `CAN_DOCK`, and only moves when the building's `0x12` receiver path installs a destination. Rust does have the important accepted-cell recheck shape at `src/sim/miner/miner_dock_sequence.rs:632-649`.

Rust abort paths at `src/sim/miner/miner_dock_sequence.rs:471-497` clear `reserved_refinery`, `dock_queued`, and movement state when the refinery is invalid. The binary abort gate inside `0x004D9290` is narrower: a non-ROGER `CAN_DOCK` only breaks/clears when `+0x418 == 0`; with `+0x418 != 0` it preserves Mission Enter.

## 8. Open Questions - Final State of Investigation Log

- `[RESOLVED] OQ-1 - Is 0x004D9290 the actual active mission handler for mission 7? -> Yes; `MissionClass::Mission_Dispatch` case 7 dispatches vtable `+0x240`, and vtable data xrefs point at `0x004D9290`.` (evidence: `0x005B3060`, xrefs `0x007E8ED4/0x007EB298/0x007F5EB0`)`
- `[RESOLVED] OQ-2 - Does Mission Enter send repeated CAN_DOCK? -> Yes, every time mission dispatch invokes `0x004D9290` with a contact/fallback target, it transmits `0x0E` before path/NavCom handling.` (evidence: `0x004D92B2..0x004D92BF`)`
- `[RESOLVED] OQ-3 - Is retry per tick or timer-gated? -> Timer-gated by mission dispatch return, not a hard-coded per-tick loop; the epilogue returns mission timer entry * 900.0 plus `RandomRanged(0,2)`.` (evidence: `0x004D946C..0x004D9497`, `0x005B3060`, `0x005B3A00`)`
- `[RESOLVED] OQ-4 - Does Mission Enter read art `QueueingCell=`? -> No; `0x004D9290` has no BuildingType `+0x1618/+0x161C` read, and the verified building `0x0E` accepted-cell path is hardcoded `anchor+(3,1)`.` (evidence: `0x004D9290`, `0x0043C2D0` sibling reports)`
- `[RESOLVED] OQ-5 - What preserves the refinery target after a non-ROGER CAN_DOCK? -> Byte `+0x418` nonzero bypasses the break/clear abort path.` (evidence: `0x004D92BF..0x004D92CC`)`
- `[RESOLVED] OQ-6 - What aborts contact after CAN_DOCK failure? -> If return != 1 and `+0x418 == 0`, Mission Enter sends `BREAK(3)` then calls vtable `+0x484(0,1)`.` (evidence: `0x004D92CE..0x004D92E8`)`
- `[RESOLVED] OQ-7 - Where is accepted-cell movement installed? -> `FootClass::Receive_Radio` case `0x12`, not `0x004D9290`; it calls SetDestination with the payload and resets retry/timer fields.` (evidence: `0x004D8FB0`, `0x004D94B0`)`
- `[RESOLVED] OQ-8 - What happens if no contact target exists? -> Mission Enter filters `+0x218`; if no valid target and no helper retarget, it clears movement/mission path through vtable `+0x484(0,1)` then calls vtable `+0x1EC`.` (evidence: `0x004D929B..0x004D9466`)`
- `[RESOLVED] OQ-9 - Is HELLO/contact FIFO owned by Mission Enter? -> No; `0x004D9290` only consumes contact slot 0 and does not manage a FIFO. Rust's `waiting_retry_queue` is an implementation-side structure, not verified in this handler.` (evidence: `0x0065AD30`, `0x004D9294`)`
- `[DEFERRED] OQ-10 - What exact frame count does the mission timer table give for mission 7 in a running YR process?` (category: `needs-runtime-debugger`; reason: table appears runtime/static-data dependent and this slot did not use runtime memory inspection; next-step-if-pursued: break after `0x005B3A00` for a Mission Enter unit and read the loaded double before `ftol`)`
- `[DEFERRED] OQ-11 - Which non-refinery enter paths rely on the same `+0x418` preserve gate?` (category: `out-of-scope`; reason: scope is refinery retry/queue only; next-step-if-pursued: run a separate repair/hospital/transport Mission Enter slice)`

### Negative Facts / Do Not Do

- Do not put FIFO queue ownership inside `0x004D9290`; it only reads contact slot `0` and target fallback. Evidence: `0x0065AD30`, `0x004D9294`.
- Do not read `QueueingCell=` for Mission Enter retry or the accepted `CAN_DOCK` cell. Evidence: no `+0x1618/+0x161C` reads in `0x004D9290`; building `0x0E` sibling reports hardcoded `+3,+1`.
- Do not abort a harvester's refinery target on every non-ROGER `CAN_DOCK`; `+0x418 != 0` explicitly preserves the path. Evidence: `0x004D92C4..0x004D92CC`.
- Do not model `0x12` as a delayed queue admission side effect; it immediately calls SetDestination for non-already-there payloads and clears mission dispatch duration. Evidence: `0x004D8FB0`, `0x004D94B0`.
- Do not use the old `0x00739EC0` Mission Enter doc as the identity source for this slice; that report documents per-cell choreography and has label drift. Evidence: current `0x004D9290` decompile and mission dispatch `+0x240`.

### Remaining Uncertainty

- Exact runtime mission timer value for mission ID `7` was not decoded; the formula and random `0..2` jitter are verified, but not the base frame count.
- Full non-refinery consumers of the `+0x418` preserve gate were not investigated.
- The binary source of any non-contact "waiting FIFO" outside standard RadioClass `Contacts[]` was not found in `0x004D9290`; if slot 1 finds a building-side retry queue, reconcile it with this negative finding.
