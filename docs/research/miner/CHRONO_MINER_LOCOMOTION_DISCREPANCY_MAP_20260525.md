# Chrono Miner Locomotion Discrepancy Map

**Date:** 2026-05-25  
**Investigation Mode:** coverage-map  
**Claimed Scope:** current Rust vs existing verified `gamemd.exe` research for stock YR Chrono Miner locomotion: ore approach, full-cargo return, far-return teleport staging, dock entry, unload/departure, and locomotor/facing state.  
**Non-Scope:** fresh binary decompilation, runtime frame capture, full A* parity, full render/audio composition, and implementation patches.  
**Confidence:** High for mismatches backed by existing HIGH-confidence Ghidra reports and current Rust source scan; Medium for live-frame/player-visible ranking where no runtime capture was available.  
**Active in YR:** Yes for stock `[CMIN] Harvester=yes`, `Teleporter=yes`, `Dock=NAREFN,GAREFN`, and stock refinery `DockUnload=yes`.

## 1. Overview

The old major discrepancy "CMIN uses a 2-cell return threshold" appears fixed in current Rust: the current code parses `ChronoHarvTooFarDistance=50`, compares 3D lepton distance, and uses strict `>` for the far path.

The remaining high-leverage locomotion discrepancies are around the exact locomotor mechanism rather than the broad harvest loop: the active Teleport/Drive piggyback lifecycle is not represented, far-return nearby-cell fallback has verified search differences, dock radio `0x16` is currently collapsed into an explicit East body-facing pivot even though the binary path goes through locomotor `+0x4C(0x4000)` / `RateTimer` semantics and the exact body-facing equivalence is unresolved, CMIN/HARV `ROT=` is parsed as `10` in Rust though the verified runtime-facing field remains `5`, and the unload path uses the reserved refinery ID instead of gamemd's adjacent-cell refinery rediscovery.

## 4. Stale Or Conflicting Prior Claims

- `CHRONO_MINER_FAR_RETURN_FALLBACK_DESTINATION_GHIDRA_REPORT.md` section 6 previously said current Rust still used a hardcoded 2-cell chrono inbound threshold; it now carries a 2026-05-25 repo-status supersession. The newer close/far split report and current source scan show this has been fixed for stock values.
- Older trace material that treats normal stock post-unload `Force_Track(0x47)` as always active conflicts with the later zero-link/reciprocal-link reports. Treat Force_Track as conditional linked/interrupt behavior, not normal healthy DockUnload completion.
- `CHRONO_MINER_LOCOMOTION_DRIVE_PHASE_TRACE.md` contains a strong claim that CMIN should warp to ore. That conflicts with `CHRONO_MINER_SYSTEM_OVERVIEW.md` and current implementation comments that state CMIN drives to ore. Do not implement an ore-approach warp from that trace alone; rerun `/re-investigate chrono miner ore approach teleport-vs-drive` if this is still disputed.

## 5. Suggested Fix Order

1. Fix the parser/source ROT mismatch first. It is narrow, verified, and affects all downstream facing/drive/dock timing surfaces.
2. Replace the fabricated East-facing dock pivot with the audited `0x16` sync/wait/send-`0x15` semantics. This is the most important dock-entry behavior mismatch.
3. Correct the CMIN far-return fallback nearby-cell helper: radius cap, 24-candidate cap, direct/indirect preference, and frame modulo.
4. Add a gamemd-style unload refinery rediscovery path for the zero-link FSM before relying on `reserved_refinery` for state-3/state-4 behavior.
5. Plan a dedicated locomotor-piggyback investigation/implementation contract. This is broader and should be split from dock/rules fixes.
